Day 02
Phase 01 · Foundation
Velocity Fraud Detection Query
SQL Window Functions
Effort
4–5 hrs
What To Do
  • Understand the concept: velocity fraud = a card making too many transactions in a short time window (e.g., more than 5 transactions within 10 minutes)
  • Learn and apply SQL Window Functions: specifically COUNT() OVER (PARTITION BY card_id ORDER BY timestamp RANGE BETWEEN INTERVAL '10 minutes' PRECEDING AND CURRENT ROW)
  • Write velocity_fraud.sql — a CTE-based query that calculates a rolling transaction count per card per time window, then flags cards where the count exceeds a configurable threshold
  • Test the query directly in DuckDB shell — verify it flags your injected fraud seeds from Day 1
  • Add a risk_score column: the higher the velocity, the higher the score (simple formula: txn_count / threshold * 10)
  • Store query results in a view: CREATE OR REPLACE VIEW velocity_flags AS ...
  • Document the query with inline SQL comments explaining each CTE step
Tools & Resources
📊 DuckDB CLI / Python Run and test SQL directly. DuckDB supports INTERVAL-based window frames natively
💡 Mode Analytics SQL School Free interactive tutorial on window functions — covers PARTITION BY, RANGE vs ROWS
DuckDB Window Functions Docs — RANGE BETWEEN syntax
Mode SQL Window Functions Tutorial — best free resource
Search: "rolling count window function fraud detection SQL" on StackOverflow for real-world examples
Key SQL Concept (study this)
WITH rolling_counts AS ( SELECT transaction_id, card_id, timestamp, amount, COUNT(*) OVER ( PARTITION BY card_id ORDER BY timestamp RANGE BETWEEN INTERVAL '10 minutes' PRECEDING AND CURRENT ROW ) AS txn_count_10min FROM transactions ) SELECT * FROM rolling_counts WHERE txn_count_10min > 5; -- threshold
Why This Matters for Interviews
  • Interviewers at Flipkart, Paytm, Razorpay always ask window function questions
  • RANGE BETWEEN INTERVAL is an advanced pattern very few candidates know
  • CTEs show structured thinking — always preferred over nested subqueries

Day 03
Phase 02 · Core Detection
Geographic Impossibility Detection
SQL Self-Joins LAG()
Effort
4–5 hrs
What To Do
  • Understand the fraud type: the same card was used in two different cities within a physically impossible time gap (e.g., Delhi at 9:00 AM and Mumbai at 9:30 AM — impossible to travel in 30 min)
  • Add city coordinates (latitude/longitude) to your dataset for at least 15–20 Indian cities during Day 1 revisit, OR use a simple city-pair lookup table
  • Write geo_fraud.sql using the LAG() window function to compare each transaction with the previous transaction for the same card: get previous city + previous timestamp
  • Calculate time gap in minutes between consecutive transactions per card using timestamp arithmetic
  • Flag transactions where: city changed AND time gap < minimum_travel_time between those cities
  • Create a city-distance reference table (simple approach: hardcode 10–15 city pairs with realistic min travel times in hours)
  • Test query — verify it catches your injected "impossible geography" seeds
Tools & Resources
🗺️ LAG() Window Function Accesses the previous row's value within a partition — perfect for comparing consecutive transactions per card
🔗 Self-Join Pattern Alternative approach: join transactions table to itself on card_id with time constraints to find co-occurring records in different cities
DuckDB Timestamp Functions — for time difference calculations
Search: "detect impossible travel SQL LAG window function" — multiple real bank fraud examples available
GeeksForGeeks LAG() tutorial — clear explanation with examples
Key SQL Concept (study this)
WITH consecutive_txns AS ( SELECT card_id, city, timestamp, LAG(city) OVER (win) AS prev_city, LAG(timestamp) OVER (win) AS prev_ts FROM transactions WINDOW win AS ( PARTITION BY card_id ORDER BY timestamp) ) SELECT * FROM consecutive_txns WHERE city != prev_city AND DATEDIFF('minute', prev_ts, timestamp) < 60;
Why This Matters for Interviews
  • LAG() / LEAD() are among the top 5 most-tested SQL functions in DE interviews
  • Shows you can model real-world business logic in SQL — not just aggregates
  • Self-join pattern is a common interview question itself

Day 04
Phase 02 · Core Detection
Amount Deviation from Historical Baseline
SQL Statistics Z-Score
Effort
4–5 hrs
What To Do
  • Understand the concept: each card has a historical spending baseline (avg amount + standard deviation). A transaction is suspicious if its amount is far from the baseline — measured using Z-score = (amount - avg) / stddev
  • Write amount_deviation.sql in two parts: (1) compute per-card historical baseline using AVG() and STDDEV(), (2) flag transactions where Z-score exceeds 3.0 (3 standard deviations from mean)
  • Use a CTE chain: first CTE computes baselines, second CTE joins back to transactions, third CTE applies the Z-score threshold filter
  • Add a category label: CASE WHEN z_score > 5 THEN 'HIGH' WHEN z_score > 3 THEN 'MEDIUM' END
  • Handle edge case: cards with fewer than 10 historical transactions should be excluded from baseline (not enough history)
  • Verify the query catches your large-amount fraud seeds from Day 1
Tools & Resources
📐 DuckDB STDDEV_POP / STDDEV_SAMP Built-in aggregate functions for standard deviation. Use STDDEV_SAMP for sample-based datasets
🧮 Z-Score Formula (amount - avg_amount) / NULLIF(stddev_amount, 0) — NULLIF protects against division by zero
DuckDB Aggregate Functions — AVG, STDDEV, VARIANCE
Khan Academy: "Z-scores and percentiles" — understand the concept in 10 minutes
Search: "Z-score anomaly detection SQL" on Medium for walkthrough articles
Key SQL Concept (study this)
WITH baselines AS ( SELECT card_id, AVG(amount) AS avg_amt, STDDEV_SAMP(amount) AS std_amt, COUNT(*) AS txn_count FROM transactions GROUP BY card_id HAVING COUNT(*) >= 10 -- min history ), scored AS ( SELECT t.*, (t.amount - b.avg_amt) / NULLIF(b.std_amt, 0) AS z_score FROM transactions t JOIN baselines b USING(card_id) ) SELECT * FROM scored WHERE z_score > 3.0;
Why This Matters for Interviews
  • Applying statistical concepts in SQL is a rare skill that senior DE roles specifically test
  • HAVING clause + CTE chains + NULLIF edge case handling — all common interview questions
  • Z-score is used in real fraud systems at Paytm, PhonePe, HDFC
